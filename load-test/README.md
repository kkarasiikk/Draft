# Навантажувальне тестування

Оснастка, щоб перевірити, скільки витримує бекенд, **не сплативши за це
рахунком і не наразивши прод-проєкт на автозахист Google**. За замовчуванням
усе б'є по локальному емулятору Firebase, а не по бойовому Firebase.

## Чому не по проду

Проєкт на тарифі Blaze — оплата за виклик. Реальний стрес-тест на бойовий
Firebase означав би тисячі платних викликів функцій, читань/записів Firestore
(а `aiChat` ще й платний Anthropic API), плюс ризик, що Google призупинить
проєкт за схожість трафіку на DoS. Тому тестуємо на емуляторі: та сама логіка
функцій і правил, локально, безкоштовно.

## Запуск

```bash
npm install -g firebase-tools        # один раз
firebase emulators:start --only functions,firestore --project demo-life
```

В іншому терміналі:

```bash
# HTTP-навантаження на walletSync (сира пропускна здатність функції)
node load-test/hammer.mjs --rps 100 --seconds 20

# Контеншн транзакцій Firestore — справжнє вузьке місце
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 node load-test/firestore-contention.mjs 50
```

`hammer.mjs` відмовиться бити по бойовому URL без явного
`--i-understand-the-cost` — це запобіжник, а не забаганка.

## Що показали виміри

### 1. Емулятор функцій throughput не міряє

Локальний емулятор ганяє функції в кілька воркерів і серіалізує виклики: із
500 запитів за 10 с відповіли одиниці, із затримками 8–9 с. Це властивість
**емулятора**, а не проду — бойові Cloud Functions автоматично піднімають
багато інстансів. Тобто «скільки rps тримає функція» з емулятора взяти не
можна; це рахується з квот Firebase, не вимірюється локально.

### 2. Справжня стеля — конкурентні транзакції на ОДИН документ Firestore

Це вже не залежить від масштабування функцій, тож вимір показовий. І
рейт-лімітер (`walletSyncRateLimits/{ip}`), і лічильник AI-чату
(`aiChatRateLimits/{uid}`) — це один «гарячий» документ, який
читають-і-інкрементують у транзакції.

| Конкурентних транзакцій | В ОДИН документ | У РІЗНІ документи |
|---|---|---|
| 20 | 20/20 за 3.7 с (серіалізуються) | 20/20 за 0.14 с |
| 50 | **4/50**, решта ABORTED, 21 с | 50/50 за 0.3 с |
| 100 | **5/100**, решта ABORTED, 31 с | 100/100 за 0.19 с |

Firestore серіалізує записи в один документ і **аварійно завершує**
(код 10, ABORTED) конкурентні транзакції понад свою межу. Різні документи —
паралельні, стелі майже немає.

## Висновки для цього застосунку

- **Один нападник (один IP / один юзер) сайт не покладе.** Його ж запити
  б'ються за один гарячий документ рейт-лімітера, серіалізуються й
  аварійно завершуються. Гарячий документ сам себе throttle'ить — це радше
  на користь.
- **Обхід — розподілений ботнет (багато IP).** Різні документи йдуть
  паралельно, тож per-IP ліміт ботнет не спиняє: кожен IP отримує власний
  бюджет 20 запитів, кожен запит = 1 транзакція лічильника + 1 запит
  `users.where(walletSyncKey==key)` = 2 операції Firestore. Сайт не
  «ламається» (статику тримає CDN, функції масштабуються), але це дренаж
  квоти читань і Blaze-бюджету.
- **Рейт-лімітер fail-open за задумом.** Транзакція ліміту обгорнута в
  try/catch, що ковтає помилку й пропускає запит далі (щоб збій лімітера не
  блокував легітимну синхронізацію). Плата за це — ліміт є best-effort, а не
  жорстка гарантія: якщо шлях до Firestore деградує, throttle тихо зникає.
  (Саме це видно в емуляторі, де admin SDK підмінений — у проді вираз
  `admin.firestore.FieldValue.increment` робочий, це не баг коду.)

## Якщо все ж хочеться помірити прод

Свідомо, розуміючи ціну й ризик:

```bash
node load-test/hammer.mjs \
  --url https://<region>-<project>.cloudfunctions.net/walletSync \
  --rps 10 --seconds 10 \
  --i-understand-the-cost
```

Тримай `--rps` низьким (одиниці), інакше платиш за кожен виклик і ризикуєш
автозахистом Google. Порядок надійніше — з Google Cloud Monitoring
(вкладка проєкту → Cloud Functions → метрики), ніж із зовнішнього обстрілу.

## Запобіжники вартості

Стрес-тест показав: єдиний реальний вектор — не «поломка», а **дренаж
бюджету** розподіленим ботнетом. Проти нього два кроки.

### 1. Стеля інстансів (уже в коді)

`maxInstances` на функціях — головний запобіжник, бо він не *повідомляє* про
перевитрату, а *не пускає* її: скільки б запитів не летіло, більше N
інстансів не підніметься.

| Функція | maxInstances | Чому саме так |
|---|---|---|
| `walletSync` | 10 | публічна, але дешева (лише Firestore); 10 — з запасом |
| `aiChat`, `goalBreakdown` | 5 | платні за токенами; + ліміт 30 повідомлень/10 хв на юзера |
| `taskReminders` | 2 | планова, страховка від накладання запусків |

Застосовується на `firebase deploy --only functions`. Легітимному
одному-двом користувачам ці стелі не відчутні.

### 2. Бюджетний алерт (треба зробити в консолі — я не маю доступу)

Алерт живе в Google Cloud Billing, не в репозиторії. Два способи.

**Console (2 хвилини):** Google Cloud Console → Billing → Budgets & alerts →
Create budget → назва «Life», обери проєкт `me-and-only-me-7f531` → сума,
напр. **$5/міс** → пороги сповіщень 50% / 90% / 100% → лист приходить на
Billing-адміна. Це лише сповіщення, витрати воно не ріже — жорстку стелю
дає `maxInstances` вище.

**gcloud (якщо є CLI):**

```bash
# id білінг-акаунта
gcloud billing accounts list

# бюджет $5/міс зі сповіщеннями на 50/90/100%
gcloud billing budgets create \
  --billing-account=BILLING_ACCOUNT_ID \
  --display-name="Life budget" \
  --budget-amount=5USD \
  --filter-projects=projects/me-and-only-me-7f531 \
  --threshold-rule=percent=0.5 \
  --threshold-rule=percent=0.9 \
  --threshold-rule=percent=1.0
```

Заміни `BILLING_ACCOUNT_ID` на свій із першої команди. Це разова дія.
